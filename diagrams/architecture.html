Architecture · v0 build plan · 2026-10-12

God Tier: a harness of harnesses

One local layer that any harness, SDK, model CLI, API or website can join. It hands out tasks, keeps members from wiping each other's work, fails over when a subscription runs out, and checks what was really done. It has no model of its own and never holds anyone's keys.

1. The whole system

You talk to the core through the board and the CLI. The core drives every member through a driver. Members that can use the shared tools work live in your repo under reservations; everything else works in its own sandbox copy and is merged only after the acceptance check.

2. Inside the core: one task, start to finish

Every task passes the same four stations. Four of them can raise a hold, which is the only way the system ever asks you anything. Everything is written to the event log, so gt why can explain any decision.

3. Onboarding: how anything becomes a member

gt add <anything>. Protocol speakers go straight to a bridge. Everything else goes to the onboarding agent, which reads the help text, README or page and writes a driver spec. Nothing is enrolled until it passes conformance, and a version change or rising failures send it back for repair.

4. Every surface, one way in

How much a member can be steered depends on its surface. Whether it can join never does.

5. Proven, planned, and fixed

Tested 2026-10-12

What the tests proved

  • Rules in the prompt channel: 18/18 followed; in tool descriptions only 5/18
  • Live two-agent trials: whole work wiped 2/6 without protocol, 0/12 with
  • Intake check on blind pairs: 14/14 contradictions caught, 1/14 false flag
  • Agents said done 36/36, really done 19/36; acceptance check caught 17/17
  • Onboarding from help text: 3/3 passed conformance first try

v0 build order

What gets built first

  1. Core store, event log, task and result shapes
  2. Bridges and the reference harness
  3. Onboarding agent + conformance for CLI, SDK, TUI
  4. Rules delivery, shared tools, reservations
  5. Intake check and acceptance check
  6. Quota meter and failover
  7. Sandbox + merge, website doors
  8. Board and gt.yaml

Stable contracts

What never changes

  • Task shape: goal, done list, resources
  • Result shape: status, content, evidence
  • Five hold types, one key each
  • Levels L0 to L4
  • Everything else is swappable: drivers, judge models, board, bridges
